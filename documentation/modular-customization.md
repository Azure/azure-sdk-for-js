# Modular SDK Customization Guide

Use this workflow for modular TypeScript SDKs generated by `@azure-tools/typespec-ts`.

The recommended layout keeps generated source in `src/generated/`. Keep handwritten source in
the other `src/` folders. The generator does not merge these files.

## Before You Customize

First, try to make the change in TypeSpec. TypeSpec changes are easier to maintain.

See the
[TypeSpec Client Customizations Reference](https://github.com/Azure/azure-sdk-tools/blob/main/eng/common/knowledge/customizing-client-tsp.md)
for supported decorators.

Use handwritten TypeScript only when TypeSpec cannot make the required change.

## Set Up the Package

Run this command from the package directory:

```bash
npx dev-tool customization init
```

For an existing merge-based package, the command makes these changes:

1. It moves the root `generated/` baseline to `src/generated/`.
2. It preserves the handwritten `src/` layer.
3. It removes `dev-tool customization apply` from package scripts.

For a package without a root `generated/` baseline, the command moves `src/` to
`src/generated/`. It creates facade files for the root entry point and the Warp export entry
points. It also updates package import paths and version metadata paths.

Review other package configuration files after the command completes. Update paths that still
refer to generated files under `src/`.

## Folder Structure

Use this folder structure:

```text
my-sdk-package/
  src/
    generated/
      <emitter-owned source>
    index.ts
    api/
      index.ts
    models/
      index.ts
    <handwritten source>
  test/
  README.md
  package.json
```

Do not edit files in `src/generated/`. The emitter deletes and replaces these files during each
generation.

The files outside `src/generated/` are the customization layer. These files can wrap, replace,
or re-export generated APIs.

## Customize the SDK

Edit a facade file when you must change an exported API. The initial facade exports all items
from its generated entry point:

```ts
export * from "./generated/index.js";
```

Replace the wildcard export when you must hide or replace an item. Export the handwritten item
from the same facade.

Keep new helpers and wrappers outside `src/generated/`.

## Regenerate the SDK

Run the package generation script:

```bash
npm run generate:client
```

The emitter detects `src/generated/`. It writes generated source into that directory and leaves
the other `src/` files unchanged.

Do not run `dev-tool customization apply`. The new layout does not use a three-way merge.

After generation, run the package format, build, lint, and test commands.

The template package has an end-to-end test for this workflow:

```bash
cd sdk/template/template
npm run test:generation-e2e
```

The test creates an isolated git worktree. It runs TypeSpec generation from the local
`azure-rest-api-specs` clone. It verifies the source layout and builds the package.

## Migrate a Merge-Based Package

Some packages still use a root `generated/` directory and customized copies in `src/`. These
packages use the legacy merge workflow.

Before migration, make sure that `src/` contains the correct customized source. Make sure that
root `generated/` contains the latest generated baseline. Then run:

```bash
npx dev-tool customization init
```

The command moves root `generated/` to `src/generated/`. It does not change the handwritten
`src/` layer.

Then regenerate the package. The regeneration replaces `src/generated/`. Build the package to
find handwritten files that depend on obsolete generated APIs.

## Legacy Merge Workflow

Packages that have not migrated can continue to use:

```bash
npx dev-tool customization apply
```

This command uses the root `generated/` directory and performs a three-way merge into `src/`.
Merge conflicts can occur. Migrate these packages to `src/generated/` when practical.
