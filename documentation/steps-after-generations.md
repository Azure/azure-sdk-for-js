What to do after generating the SDK code
===========================================================================

Generated code is only the starting point. After generation, validate the
package, add tests and samples, and prepare the package for CI and release.

# Build your project

After generation, install dependencies and build the package from the repo
root. For workspace packages, always use Turbo so dependent packages are built
in the correct order.

```shell
pnpm install
pnpm turbo build --filter=<your-package-name>... --token 1
```

For the overall SDK workflow, see the [development workflows guide](../CONTRIBUTING.md#development-workflows).

# Customizing the generated code

If the generated code does not fit your needs, prefer TypeSpec changes first.
If JavaScript customizations are still required, use the modular customization
workflow described in the [Modular (DPG) Customization Guide](./modular-customization.md).

# Generate `CHANGELOG.md`

Install the release tooling dependencies:

```shell
npm --prefix eng/tools/js-sdk-release-tools ci
```

Then run the changelog tool:

```shell
npm --prefix eng/tools/js-sdk-release-tools exec --no -- changelog-tool <your-package-path>
```

Example:

```shell
npm --prefix eng/tools/js-sdk-release-tools exec --no -- changelog-tool sdk/advisor/arm-advisor
```

# How to write tests for DPG/RLC/MPG

To release a package, add runnable tests. Generated packages typically include a
starter test under `test/public/sampleTest.spec.ts` that you can replace or
expand.

See the [JavaScript Codegen Quick Start for Test](./Quickstart-on-how-to-write-tests.md)
for the recorder/test-proxy workflow.

1. **Write the test**

   Follow the [basic RLC test interaction and recording example](./Quickstart-on-how-to-write-tests.md#example-1-basic-rlc-test-interaction-and-recording-for-azure-data-plane-service)
   and adapt it to your service.

   More examples:
   - RLC example: [Maps Route tests](../sdk/maps/maps-route-rest/test/public)
   - DPG example: [OpenAI tests](../sdk/openai/openai/test/public)
   - MPG example: [Containerservice Fleet tests](../sdk/containerservice/arm-containerservicefleet/test/public)

2. **Run the tests**

   Build first, then run tests from the package directory. Set `TEST_MODE=record`
   the first time so recordings are generated.

   Linux/macOS:

   ```shell
   pnpm turbo build --filter=${PACKAGE_NAME}... --token 1
   export TEST_MODE=record
   pnpm test
   ```

   Windows CMD:

   ```shell
   pnpm turbo build --filter=%PACKAGE_NAME%... --token 1
   set TEST_MODE=record
   pnpm test
   ```

   To run with existing recordings:

   Linux/macOS:

   ```shell
   pnpm turbo build --filter=${PACKAGE_NAME}... --token 1
   export TEST_MODE=playback
   pnpm test
   ```

   Windows CMD:

   ```shell
   pnpm turbo build --filter=%PACKAGE_NAME%... --token 1
   set TEST_MODE=playback
   pnpm test
   ```

# How to write samples

Author TypeScript samples under `samples-dev`. For a template, see
[the samples-dev template](../sdk/template/template/samples-dev).

Examples:
- DPG sample: [OpenAI samples](../sdk/openai/openai/samples-dev)
- RLC sample: [Maps Route samples](../sdk/maps/maps-route-rest/samples-dev)

After adding `samples-dev`, make sure the package `tsconfig.json` includes the
samples and that the package can resolve its local source during sample builds.
A typical `paths` entry looks like:

```json
"paths": { "@azure/agrifood-farming": ["./src/index"] }
```

And `include` should contain:

```json
"include": ["./src/**/*.ts", "./test/**/*.ts", "samples-dev/**/*.ts"]
```

Add sample metadata to `package.json`:

```json
"//sampleConfiguration": {
  "productName": "A description of your service",
  "productSlugs": ["azure"],
  "disableDocsMs": true,
  "apiRefLink": "<the-link-to-your-service-on-learn.microsoft.com>"
}
```

Then publish generated samples:

```shell
npx dev-tool samples publish -f
```

The generated JavaScript and TypeScript samples will appear in `samples/`.

# Adding a new third-party runtime dependency

Shipped client and management libraries (those with `"sdk-type": "client"` or
`"sdk-type": "mgmt"` in `package.json`) may not take a new third-party runtime
dependency without approval. This is enforced in CI by the
`@azure/azure-sdk/ts-package-json-approved-dependencies` ESLint rule, which
validates the `dependencies` field against a central allow-list in
[`eng/approved-third-party-dependencies.yml`](../eng/approved-third-party-dependencies.yml).

First-party dependencies are always allowed and do not need to be listed:
`@azure/`, `@azure-rest/`, `@azure-tools/`, `@microsoft/`, and `@typespec/`.

To take a new third-party runtime dependency:

1. Get the dependency approved.
2. Add it to `eng/approved-third-party-dependencies.yml`:
   - under `allowed` if every package may use it
   - under `exceptions` if only specific packages may use it

Example scoped exception:

```yaml
exceptions:
  - dependency: some-package
    packages:
      - "@azure/your-package"
```

Scope wildcards such as `@opentelemetry/*` are supported.

# Create a package artifact

To build a releasable artifact locally:

```shell
pnpm install
pnpm turbo build --filter=<your-package-name>... --token 1
cd <your-sdk-folder>
pnpm test
pnpm pack
```

If recordings must be updated first, run the tests with `TEST_MODE=record`
before packaging.

# Create or update `ci.yml`

Before opening a PR, make sure the package has the correct CI file.

- If this is a new data-plane package, add `ci.yml`.
- If this is a new management-plane package, add `ci.mgmt.yml`.
- If the file already exists, update the `Artifacts` list with your package.

Use an existing package in the same service area as a template rather than
copying an old static snippet. Current CI templates live under
`eng/pipelines/templates/stages/`.

# Prepare the PR

## `CHANGELOG.md`

Update the changelog with customer-facing changes. Follow the current Azure SDK
format and keep the top entry as `(Unreleased)` until release.

## Version number

Update the package version according to semantic versioning and Azure SDK
versioning policy.

## Test recordings

After [writing and running tests](#how-to-write-tests-for-dpgrlcmpg), push
updated recordings to `Azure/azure-sdk-assets` using the steps in
[Quickstart-on-how-to-write-tests.md](./Quickstart-on-how-to-write-tests.md#how-to-push-test-recordings-to-assets-repo).

## Fix CI for the PR

If CI fails, see [Troubleshoot CI Failure](./Troubleshoot-ci-failure.md).

## Resolve conflicts for the PR

If `pnpm-lock.yaml` conflicts after rebasing or merging from `main`, follow
[Resolve pnpm-lock Merge Conflicts](./resolve-pnpm-lock-merge-conflict.md).

## AutoPR branches

AutoPRs may come from the `azure-sdk/azure-sdk-for-js` fork rather than your
`origin` remote. If needed, use VS Code's GitHub Pull Requests extension or add
that fork as a separate remote and fetch the branch explicitly.

## CC `dpg-devs` for review

If requested by your team workflow, add:

```text
cc @Azure/dpg-devs for awareness
```

# Release

Prepare the SDK for release using the release plan process. The release plan
contains the required approvals, testing expectations, documentation steps, and
pipeline guidance. See the Azure SDK release-plan documentation at
<https://eng.ms/docs/products/azure-developer-experience/plan/release-plan>.
